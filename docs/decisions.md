# Decision Log

Numbered, append-only. To change a decision, add a new entry that supersedes the old one (and mark the old one **Superseded by Dn**). `design-doc.md` is the feature spec; this file records how and why we chose.

---

## D1 — React Native + TypeScript (strict), via Expo
*2026-11-05*

**Decision:** Build with React Native and TypeScript in strict mode (`strict`, `noUncheckedIndexedAccess`), using Expo (SDK 58) and Expo Router.

**Why:** The owner knows TS/JS but not Dart and wants to be able to read and modify the code. Flutter's advantages (sound typing, simpler APK pipeline, slightly faster startup) are real but small for an app this size.

**Alternatives:** Flutter/Dart (strongest technical fit, unfamiliar language); Kotlin Multiplatform + Compose (iOS side less mature).

## D2 — One feature per task, with an APK review between each
*2026-11-05*

**Decision:** Each numbered feature in `design-doc.md` is its own task, in order, preceded by a foundation task. Each ends with a release APK that the owner installs and reviews before the next starts.

**Why:** Owner's preferred review cadence; keeps feedback tight.

## D5 — Local builds by default; CI runs fast checks only
*2026-11-05*

**Decision:** Release APKs are built on the dev machine (`npm run apk`) and published to GitHub Releases with `npm run release`. GitHub Actions runs only `npm run check` (lint + typecheck + tests). Day-to-day UI iteration uses Expo Go over LAN.

**Why:** Fast feedback loop; Android builds on CI take 8-12 minutes. The repo is public, so CI minutes aren't the constraint; speed is.

**Details:**
- `android/` is generated by `expo prebuild` and gitignored (Continuous Native Generation).
- Release signing via `plugins/withReleaseSigning.ts`, fed by `~/.gradle/gradle.properties`. The keystore lives at `~/.caster-companion/release.keystore`, outside the repo, and must be backed up or future APKs won't install over old ones.
- `package.json` `version` is the single source of truth. The Android `versionCode` is derived from it (`major*10000 + minor*100 + patch`).
- APKs are arm64-v8a only, which covers essentially all current Android phones and keeps builds fast and the APK small.

## D9 — Windows builds: long paths + CMake 3.31
*2026-11-05*

**Decision:** Local Android builds on Windows require the `LongPathsEnabled` registry setting, plus SDK CMake 3.31.6. `scripts/build-apk.ts` pins it via `cmake.dir` in `android/local.properties`.

**Why:** Expo Router depends on `react-native-reanimated` and `react-native-gesture-handler`, whose CMake builds produce object-file paths of about 300 characters. The SDK's default CMake 3.22 ships ninja 1.10, which can't use Windows long paths; CMake 3.31's ninja 1.12 can.

**Alternatives tried or rejected:**
- A `subst` drive: Expo autolinking can't find `package.json` at a drive root.
- Moving the repo to a short path: only a few characters of margin.
- Building APKs in CI: slower, and contradicts D5.
- CMake 4.x: drops compatibility with old `cmake_minimum_required` values that some React Native libraries still use.

## D10 — Mission Point Tracker interaction (feature 1)
*2026-11-06*

**Decision:**
- Each player's half shows one large number. Tap the right side of a half for +1 and the left side for −1. The rotation from D7 makes "right" correct for the player across the table.

## D11 — Local persistence via AsyncStorage
*2026-11-06*

**Decision:** Game state is saved to `@react-native-async-storage/async-storage` on every change and restored on launch, so a game survives the app being killed. `src/storage/persisted.ts` wraps it. Every read goes through a parser, so corrupt or old-format data falls back to defaults. Keys are versioned (e.g. `tracker.missionPoints.v1`).

**Why:** Tiny, works in Expo Go, and the data is a few numbers.

**Alternatives:** `expo-sqlite/kv-store` (synchronous reads, but pulls in SQLite).

## D13 — Priority Tracker and new-game flow (feature 2; amends D12)
*2026-11-06*

**Decision:**
- **Start screen.** A new game opens on three sections: one per player ("I go first", with the top section rotated) and a middle "Flip a coin" button. The coin result shows for 1.5 s (winner highlighted, loser dimmed, all buttons disabled), then the game starts.
- **Showing priority.** The player going first gets a bright gold frame and a raised, tappable `FIRST ⇅` badge on the edge of their half nearest the middle band. The other half's frame is dimmed.
- **Passing priority.** Tap the badge to hand priority to the other player. There's no separate band button, so D12's reserved right slot is now spare.
- **Reset is "new game".** It clears mission points and priority (and, later, round and timer), then returns to the start screen.
- **State model.** Scores and priority now live in one `GameState` reducer (`src/domain/game.ts`), saved under `tracker.game.v1`. Scores saved by v0.2.x (`tracker.missionPoints.v1`) carry over. The UI waits for saved state to load, so it never flashes the start screen for a game in progress.

**Why:** Owner's choices. The badge doubles as indicator and control, keeping the band uncluttered. One reducer gives features 3 and 4 a single place to hook "priority passed means next round".

## D15 — Themed dialogs replace native alerts
*2026-11-07*

**Decision:** Confirmations use an in-style dialog instead of the native `Alert`. `DialogProvider` (mounted once in the root layout) hosts a single `ThemedDialog`: a card-framed panel over a dimmed screen. Screens call `const { confirm } = useDialog(); if (await confirm({ title, message, confirmLabel, destructive })) …`. Tapping outside the panel or pressing the Android back button cancels. A destructive confirm gets a coral warning button; otherwise it's moon-lime. Its buttons use `TagButton`, the shared cartoon-tag button that the coin flip and FIRST badge now use too.

**Why:** The owner found the native popup looked out of place. One provider means every future prompt gets the style for free, and a promise-based `confirm` keeps call sites as short as `Alert.alert`.

**Alternatives:** a per-screen `<ConfirmDialog visible …/>` component (more state wiring at each call site); a router modal screen (overkill for yes/no prompts).

## D16 — Mission Point Tracker follow-ups (feature 1 sub-items; amends D10, D11)
*2026-11-07*

**Decision:**
- **Stale games start fresh.** If the app has been closed for more than 15 minutes, it opens on a new game (the start screen) instead of the saved one. "Closed" covers both a killed app (checked at launch against `tracker.lastActiveAt.v1`) and a backgrounded app (checked when it returns to the foreground). The timestamp is refreshed on launch, on every action, and on background/foreground changes. The fresh game is saved right away, so a quick reopen can't bring the old one back. Exactly 15:00 still restores; no saved timestamp (first run, or upgrading from v0.4.1) also restores. The rule lives in `src/domain/session.ts`.
- **30 mission points.** When a player reaches 30 (≥ 30), their half's background changes from the dark scrim to a translucent magenta (`colors.goalFill`), and it keeps counting with no cap. Dropping back below 30 restores the scrim. Magenta stays distinct from the moon-lime priority frame and the coral danger colour.
- **Tab order.** The tabs are now Rules · Tracker · Cryptids. The app always opens on Tracker, because it is the `/` route. Expo Router doesn't accept `initialRouteName` on the navigator, and doesn't need it here. Returning from the background keeps whichever tab was open.

**Why:** Owner's design-doc sub-items for feature 1.

**Alternatives:** storing a timestamp inside the game record (needs a v2 key and migration); highlighting only the number at 30 (less visible across the table).

## D17 — Change indicator for quick taps (feature 1 sub-item)
*2026-11-07*

**Decision:** During a burst of taps, a small outlined number beside each player's score shows the net change for that burst, e.g. `+3`, or `−2` with a true minus sign. Plus is moonlight blue; minus is coral. A burst ends 1.5 s after the last tap that changed the score (`CHANGE_BURST_MS`), and then the number disappears. The change is measured from the score before the burst, so taps that do nothing (−1 at 0) don't count. A burst that nets to zero shows nothing. The number sits in a fixed-width slot right of the score, with an equal empty slot on the left so the score stays centred (v0.4.4; v0.4.3 pinned it absolutely past the score's edge and it never appeared on the owner's device). It sits on the rotated half, so it reads correctly for the top player too. It appears and disappears without animation. Logic: `useRecentChange` (timer) plus `formatChange` (pure, `src/domain/missionPoints.ts`).

**Why:** Owner's design-doc sub-item (like the Magic Companion app). A net value answers "how much did I just add?" even after a correction tap.

**Alternatives:** counting taps instead of the net change (wrong after a correction); a fade-out animation (can add if wanted).

## D18 — Change indicator fades out (amends D17)
*2026-11-07*

**Decision:** After each change, the burst indicator stays fully visible for 0.5 s (`CHANGE_HOLD_MS`), then fades linearly to transparent over 1 s (`CHANGE_FADE_MS`). The fade reaches zero exactly when the 1.5 s burst ends (`CHANGE_BURST_MS` is defined as their sum). Each new change snaps it back to full strength and restarts the timing. It uses core `Animated` with the native driver, so no new dependency.

**Why:** Owner wanted players to see when the burst is about to expire. A short hold keeps the number readable right after a tap.

**Alternatives:** fading over the whole window (dims immediately, harder to read); a shrinking progress ring (busier).

## D19 — Round counter in a side drawer (feature 3; amends D12, D13)
*2026-11-07*

**Decision:**
- **Counting.** `GameState` gains `round`. A game starts at round 1, and each priority pass (the FIRST badge) starts the next round. New game resets to 1. There's no correction for mistaken passes (owner: count normally for now). It's saved in the same `tracker.game.v1` record; games saved by v0.4.x load at round 1.
- **Menu button.** A painted menu roundel (`btn-menu.png`, from `tools/art/gen_art.py buttons`) sits at the right end of the middle band, opposite reset, taking D12's spare slot.
- **Drawer.** Tapping it rolls a full-height drawer in from the right edge (30% of screen width, at least 112 dp; 220 ms ease-out, native driver), styled as a `CartoonFrame` over the strong scrim. The frame must be given `flex: 1`; v0.5.0 left it out, and on device the drawer collapsed to its top border with no content. The roundel rides on the drawer's left edge as a handle and toggles it. While it's open, a tap anywhere outside only closes it, so it can't change a score or pass priority. It starts closed in every new game.
- **Orientation.** One copy of "ROUND 3", rotated 90° clockwise to run along the drawer, perpendicular to the scores, so both players read it from the side. The text's bottom faces into the screen: most players are right-handed and reach from the right edge, so the rest of the table is "down" from the text (owner, v0.5.2; v0.5.1 rotated counter-clockwise). The timer (feature 4) will sit beside it.

**Why:** Owner's design. Keeps the table uncluttered, and one perpendicular copy is fair to both players without duplicating.

**Alternatives:** a copy facing each player (owner preferred one perpendicular copy); − / + correction buttons (deferred).

## D20 — Round timer (feature 4; amends D19)
*2026-11-07*

**Decision:**
- **What it measures.** Wall-clock time since the game started (the moment a starter is picked or the coin result is applied), shown as `05:41`, or `1:05:41` past an hour. `GameState.startedAt` (epoch ms) is set by the `start` action, which carries the time so the reducer stays pure. It's saved with the game and cleared on new game. Because it's wall-clock time, it keeps counting while the app is in the background or killed. The 15-minute stale rule (D16) still starts a fresh game after a long break. There's no pause.
- **Where.** In the side drawer, beside "ROUND n" in the same rotated row, slightly smaller and muted so the round stays the headline.
- **Ticking.** `useSyncExternalStore` reads the elapsed whole seconds fresh on every render, so the clock is right the moment the drawer opens. It polls every 250 ms only while the drawer is open. React re-renders only when the second changes.
- **Old saves.** Games saved before v0.6.0 have no start time and show `--:--` until the next new game.

**Why:** Owner's spec: a small, subtle elapsed timer revealed with the round counter.

**Alternatives:** a monotonic in-app timer (stops when the app is killed); ticking while the drawer is closed (wasted renders).

## D23 — Rules Lookup via a Gemini proxy on a Cloudflare Worker (feature 7; supersedes D3)
*2026-11-10*

**Decision:**
- **Flow.** Rules → "ASK A RULING" opens `/ask`. The player types a question (max 500 characters) and the app POSTs it to a Cloudflare Worker (`worker/`). The Worker calls Gemini (`gemini-3.5-flash-lite`, set by the `GEMINI_MODEL` var) and returns `{ answer }` or `{ error }`. The answer shows in the app as plain text, with a note that it's an unofficial AI answer and that questions go to Google.
- **Key handling.** The Gemini key comes from a free AI Studio project with **no billing account**, stored as a Wrangler secret. It never appears in the app or the repo. Google's API terms require keys to be kept confidential and forbid embedding them in open source projects, so a key in the APK was never an option. With no billing linked, abuse can only use up the free daily quota; it can never cost money.
- **Scope and abuse limits.** The Worker only answers MetaZoo rules questions, with one fixed model and system prompt, so it can't be used as general free Gemini access. It also:
  - requires an `x-app-token` header (obfuscation only, since the token ships in the app);
  - limits each IP to 5 requests a minute (Cloudflare rate-limit binding);
  - has a `KILL_SWITCH` var that turns it off.
- **Grounding.** Every request carries about 15k tokens of reference text: the official Errata & Compendium (fetched from metazootcg.com/how-to-play/errata, which robots.txt allows), plus the full rulebook and quick play PDFs (extracted with `pdftotext` and cleaned of card-image debris). The prompt tells the model the compendium wins where sources disagree, and to cite the section it used. `npm run grounding` builds `worker/src/grounding.generated.txt`; `worker:dev` and `worker:deploy` run it first. Both the source folder (`OfflineDocumentRulesReferences/`) and the generated text are gitignored: the rulebook text and the Discord export aren't ours to republish in a public repo.
- **Failures.** Errors are matched to friendly messages (`errorCopy` in `src/domain/rulings.ts`).
  - No connection: says so.
  - Rate limited: asks the player to wait.
  - Daily quota used up, Worker switched off, Gemini refusing or failing, or a 20 s timeout: offers to send the same question to ChatGPT or Claude with a prefilled link ("In MetaZoo 2025, …").
- **Shared code.** The request and response contract and question validation live in `src/domain/rulings.ts`; the Worker imports it. Worker logic (`worker/src/ask.ts`) is pure apart from the injected `fetch` and limiter, so Jest tests it in `npm run check`. `worker/src/index.ts` is a thin adapter to the Workers runtime.

**Why:** Owner's choice, after comparing chat-app handoff, bring-your-own key, an owner-hosted proxy, and on-device models. A proxy gives zero-setup answers inside the app while keeping the key secret and within Google's terms.

**Known limits:**
- The free quota is shared by every user and resets at midnight Pacific.
- Free-tier prompts may be used by Google for training and read by human reviewers.
- Gemini's terms allow only paid services for apps made available to users in the EEA (and, per the terms, Switzerland and the UK). That's fine for the owner and friends, but needs revisiting before a wide public release.

**Alternatives:** chat-app handoff only (leaves the app; kept as the fallback); bring-your-own key or "Sign in with OpenRouter" (setup for each player); an on-device model (Gemini Nano only on flagships; small open models are large downloads and weak at rulings); embedding the key (breaks Google's terms).

## D26 — Linked citations in ruling answers (amends D23, D25)
*2026-11-10*

**Decision:**
- **Citations.** The Worker's prompt asks the model to cite each source as `[Rulebook: <heading>]` or `[Compendium: <entry>]`, using exact headings from the reference text, and never to write URLs. The app's `linkCitations` (`src/domain/rulings.ts`) turns each citation into an underlined link. It also accepts the older `(Rulebook: …)` form, which the pre-D26 Worker still produces until it's redeployed.
- **Link targets.** URLs come only from the app, so the model can't invent links.
  - A compendium citation opens the errata page with a Chrome text fragment (`#:~:text=<entry>`), which scrolls to and highlights the entry. The page has no per-entry anchors.
  - A rulebook citation opens the rules web page, which is page images with no text to target.
- **Intro text.** The empty-state intro is just "Ask anything about MetaZoo rules." Dropping "Answers come from the official rulebook and errata" removes the clash with the "unofficial AI answers" note below it.

**Why:** Owner feedback on v0.9.1.

**Alternatives:** letting the model write URLs (it can invent them); linking citations to the bundled PDF (not shipped in the app, and the PDF only downloads on Android).

## D27 — Rules answers: official web pages, Google search fallback, per-minute limit (amends D23, D24, D26)
*2026-11-10*

**Decision:**
- **More official text.** `npm run grounding` now also bundles two rules pages from metazootcg.com: Organized Play (only its "How Tournaments Play" section: structure, the mulligan policy, how you win, match points, Swiss and top cut) and Dynamic Deck rules. It's an allowlist (`PAGES` in `scripts/build-grounding.ts`), not a crawl, because most of the site isn't rules. The bundle grows by about 1.3k tokens, to roughly 16.8k.
- **Citations.** The model cites these as `[Organized Play: <heading>]` and `[Dynamic Deck: <heading>]`. The app deep-links them with text fragments, like compendium entries. Labels and URLs live in `CITED_PAGES` (`src/domain/rulings.ts`).
- **Google fallback.** When the reference text doesn't cover a question and the model can't make a reasonable reading, it says so and ends with `[Search Google]`. The app turns that into a link to a Google search for the player's question, prefixed "In MetaZoo 2025, " as for the chat-app handoff. The search opens in the browser. Questions the model can reasonably read still get an answer marked unofficial, with no link.
- **Citation robustness.** Every section header in the reference text says how to cite it, because the model was copying headers ("[Full Rulebook: …]"). The app also maps the obvious variants (Full Rulebook, Quick Play, Errata) to the canonical sources. If the model returns `[Search Google]` alone, the app adds "The official rules don't cover this."
- **Per-minute limit.** Gemini returns 429 for both its per-minute and daily free-tier limits. The Worker now reads the `QuotaFailure` quota IDs and returns `rate_limited` ("try again shortly") for a per-minute limit, keeping `quota` (chat-app handoff) for the daily one or when unsure.

**Why:** Owner feedback. "How does the mulligan work?" got "the official rules do not include a mulligan", while Google's AI answer found the policy on the Organized Play page. The owner chose a Google search link over in-app search grounding.

**Rate limits** (owner's AI Studio project, `gemini-3.5-flash-lite`, free tier): 15 requests a minute, 250k input tokens a minute, 500 requests a day, all shared by every user. One request measured 15.44k tokens before this change. At ~16.8k, the token limit allows about 14.9 questions a minute, so the effective ceiling stays at about 14–15. Bundling all card text (~40k more tokens) would cut it to about 4 a minute, so card text, if added, should be matched by card name per question.

**Alternatives:**
- Gemini's Google Search grounding: not on the free tier for Gemini 3.x. It's free only on 2.5 Flash/Flash-Lite (500 a day), and its terms require showing Google's Search Suggestions snippet unmodified.
- Search only as a second request on a miss: more Worker logic, and it uses the same paid or old-model grounding.
- URL context with a fixed list of up to 20 pages: still a whitelist, fetched live on every request.
- Crawling the whole site: mostly cryptid, news and store pages.

## D28 — Rules chat scrolls to the start of a new answer (amends D25)
*2026-11-10*

**Decision:**
- **Scrolling.** While a question is waiting, the log still scrolls to the end, so the question and spinner are visible. When the answer (or error) arrives, the log scrolls once to the top of that turn, so the question sits at the top of the card and the answer reads from its first line. Later layout changes for that turn don't scroll again. The scroll position comes from the turn's `onLayout`.
- **Button label.** HOW TO PLAY stays as is; it wasn't renamed to "HOW TO PLAY VIDEOS". In the button font (Lilita One 20, letter spacing 1), "HOW TO PLAY VIDEOS" measures 213 dp. Each half-width button has roughly 120–150 dp for its label on 360–412 dp phones, so the label would wrap to two lines and make the top row about 16 dp taller, taking room from the chat when the keyboard is open.

**Why:** Owner feedback on v0.9.3. Long answers showed only their last lines; people read from the top. The label was renamed only if it didn't crowd the screen.

## D29 — Rules answers: matched card text and developer rulings (amends D23, D27)
*2026-11-11*

**Decision:**
- **Card store.** The Worker keeps every card's official text in a Workers KV namespace (`CARDS`, one key `cards`, ~250 KB). `npm run cards:seed` crawls the card pages listed in metazootcg.com's sitemap (721 printings, 604 distinct names; robots.txt allows `/card/`, only `/api` is disallowed), parses them, and uploads a precomputed match index. A Cron every 15 minutes fetches the sitemap and adds up to 2 cards it doesn't know, writing only when something changed. A new set of ~230 cards is picked up in about a day without an app update or redeploy; re-running the seed makes it immediate. Known cards aren't re-fetched: errata live in the Compendium, which overrides card text.
- **Matching (recall first).** For each question the Worker picks up to 5 cards whose names the question mentions, allowing lowercase, misspellings (up to 2 edits), shortened names (a ≥4-letter prefix, or one distinctive word of a multi-word name), plurals and split or joined words. Name words are weighted by rarity (IDF), and words that are common in the rules text ("creature", "lane") count for less. Free slots go to the next-best near matches. Reprints collapse to the newest printing. Missing a needed card is the failure to avoid; sending irrelevant ones is cheap.
- **Developer rulings.** `OfflineDocumentRulesReferences/dev-rulings.json` holds 32 short paraphrases of rulings MetaZoo's developer gave in the official Discord's gameplay-questions channel (gitignored, like the rest of that folder). A ruling is sent when it's about a matched card or two of its terms appear in the question. The model treats them as official where they apply; the Compendium wins if they conflict.
- **Request shape.** Card text and rulings go in the user turn ahead of the question, so the system instruction stays fixed. Together they're capped at ~600 tokens (cards first), which keeps the per-minute ceiling at 15 questions (250k tokens ÷ 15 = 16.7k per request; base prompt 15,977). They add no requests, so the 500-a-day limit is unaffected. Temperature is 0, so the same question gets the same ruling.
- **Citations.** `[Card: <name>]` links to the official card search (`/cards?q=<name>`); `[Dev Ruling: <title>]` links to the Discord channel. If a question names a card that isn't in the card text, the model says so and ends with `[Search Google]`.

**Why:** Owner: card-interaction questions will be the next most common kind, and they were answered "the rules don't cover specific cards… [Search Google]". The owner asked for live card data rather than a build-time bundle, and for loose matching that errs toward including cards.

**Evaluation** (28 real questions from the Discord export with known answers, `gemini-3.5-flash-lite`, `scripts/eval-cards.ts`):
- Without card text: about 6 of 26 correct; most answers punted to Google.
- With card text: 17–19 of 26, about 5 wrong (3 of them the same Static Wand ruling that exists only on Discord), 3–4 punts.
- With card text and dev rulings: 25 of 28 correct, 0 punts. Cases 1–13 were developer answers that the rulings were paraphrased from, so they flatter the result; on the 15 staff-answered cases it was 12 of 15.
- Card recall: 32 of 33 expected cards matched (the miss was a name the asker misremembered; the right card was matched).
- `gemini-3.5-flash` wasn't viable: its free quota is ~20–25 requests a day.

**Limits checked:** Cloudflare's free plan allows 10 ms CPU and 50 subrequests per request and per Cron run. Measured in Node: parsing and loading the stored index takes ~3 ms; the first match in a fresh isolate ~3–4.5 ms (cold JIT), later matches ~0.6 ms. The index is cached for 10 minutes per isolate and the rules-word list is computed once at module load, so only the first question after a cold start pays ~6–7 ms, which is close to the 10 ms limit. A Cron run makes 3 subrequests. Confirm real CPU in the Cloudflare dashboard after deploy. If requests exceed the limit, the next step is a smaller stored index (drop the joined-pair table, shorter keys); if the Cron does, drop `CARDS_PER_REFRESH` to 1.

**Alternatives:**
- Matching in the app: every phone would need the full name list, which only a full crawl produces, and a bundled list goes stale until the next sideloaded APK. It would also let clients put arbitrary text into the prompt.
- Bundling card text at build time: stale on every release, and all 721 cards (~40k tokens) per request would cut the ceiling to ~4 questions a minute.
- Calling `/cards?q=` per question: many subrequests per question with no fuzzy matching.
- Third-party card databases: none cover the 2025 sets.

## D30 — Score banner on the other tabs; games never reset while open (feature 8; amends D16)
*2026-11-11*

**Decision:**
- **Banner.** When a game is in progress (a starter has been picked), the Rules and Cryptids tabs show a slim strip at the top: `TOP 12 · BOTTOM 7 · R3`. The chip of the player with priority has the moon-lime frame, and a chip at 30+ uses the magenta goal fill, as on the tracker. It updates live. It isn't shown on the tracker, which already shows the score, or on the About modal.
- **Tap and close.** Tapping the strip opens the tracker. × hides it for the current game (identified by its start time); the next game brings it back. Closing isn't persisted.
- **Shared state.** `GameProvider` (`src/features/tracker/GameProvider.tsx`) wraps the tab navigator and owns the one `useGame()` instance, so the tracker and the banner read the same state.
- **Stale rule (amends D16).** A game never resets while the app is open, however long it sits in the background. The 15-minute rule applies only at a cold start, measured from when the app was last active. `tracker.lastActiveAt.v1` is still written on launch, on every action and on background/foreground changes, and now also once a minute while the app runs, so an app left idle and then killed isn't judged by an old timestamp.

**Why:** Design-doc feature 8, which the owner extended to the whole app with a close button. The owner corrected the stale rule: only an app that has been closed for over 15 minutes should start fresh.

**Alternatives:**
- A custom navigator header containing the banner: it changes `useHeaderHeight`, which the Rules screen's keyboard offset depends on, and means re-implementing the default header.
- A banner above the navigator: it would sit in the status-bar area, above each tab's header.
- Persisting the closed state: a closed banner would survive a cold start for no clear benefit.

## D31 — No tab headers; the score banner is a full-width top bar (amends D30)
*2026-11-11*

**Decision:**
- **Headers removed.** The Rules and Cryptids tabs no longer have a navigation header. The tab bar already names the screen, and this frees ~56 dp of height for the chat.
- **Banner.** While a game is in progress, the banner spans the full width at the top edge and runs up under the status bar. It's a solid indigo strip (`colors.surface`, like the tab bar) with an ink keyline and a shadow along the bottom. The score chips and `ROUND n` are on the left, and the × sits in its own divided cell on the right. Without a game, `ScoreBanner` only reserves the status-bar inset.
- **Keyboard.** The Rules screen's `KeyboardAvoidingView` offset is now its measured distance from the window top (below the banner), replacing the header height.
- **About.** The ⓘ button lived in the header. It moves to an "ⓘ About this app" link at the bottom of the Cryptids placeholder card, until feature 9 needs that space. It isn't on the Rules screen, where vertical space is tightest (owner).

**Why:** Owner feedback on v0.9.6: the banner didn't read as a banner, and the headers took up vertical space.

**Alternatives for About:** a link in the Rules chat's empty state (tried in a v0.9.7 build; the owner wanted that space back); a third button in the Rules link row would wrap "HOW TO PLAY" onto two lines on 360 dp phones (D28). The tracker's drawer exists only during a game. A floating corner button would collide with the banner's ×.
